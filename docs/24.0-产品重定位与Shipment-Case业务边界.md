# 24.0｜产品重定位与 Shipment Case 业务边界

> 状态：**产品方向与架构边界已经确认；24.2 之后的代码尚未开始。**
>
> 第 21～23 章不会被改写成现在的最终认识。它们分别记录了 LINK、模拟承运人和智能
> 装载能力是怎样一步步完成的。本章从现有能力出发，开始建立跨业务域的总案件。

## 1. 这一章为什么现在才出现

截至第 23 章，项目已经有三条能够独立运行的能力：

```text
LINK 订舱
→ PDF 规则解析、人工复核、七步填报、异步提交、回调、幂等和重试

模拟承运人
→ 外部系统受理、处理中、确认或拒绝，以及独立门户

智能装载
→ 箱规任务、缺失约束追问、确定性装托、3D 复核、审批、重规划和正式版本
```

这些能力本身没有做错，但它们目前使用不同的业务编号：

```text
装载任务：taskNumber
装载运行：runId
正式方案：versionId
LINK 申请：applicationNumber
承运人请求：carrierRequestId
订舱确认：bookingReference
```

系统还不知道：

> 这些编号可能属于同一票发运业务。

因此，当前平台更像“几个已经能够独立运行、但仍处于学习原型阶段的专业能力放在同一个
入口”，还不是一个能够跨步骤完成发运目标的企业 Agent 应用。

第 24 章要补的第一块地基就是：

```text
Shipment Case
```

中文统一称为：

```text
发运案件
```

---

## 2. 产品从“两个 OS”演进为什么不是推翻重做

早期门户使用：

```text
关务 OS
供应链 OS
```

这是项目当时真实的业务划分，旧笔记应该保留。

从第 24 章开始，产品的总定位升级为：

> 沙丘 TradeOps——以 Shipment Case 为核心的跨境发运智能作业系统。

这里不是删除关务和供应链，而是把它们从“两个彼此独立的产品”调整为同一案件中的不同
工作台和能力域：

```text
沙丘 TradeOps
├── 发运案件中心
├── 单证与字段证据
├── 智能装载
├── LINK 订舱
├── 关务准备
├── 人工审批
├── 异常中心
└── Agent 运行与审计
```

以后可以按角色展示不同页面：

```text
供应链人员
→ 主要查看货物、托盘、装载方案和仓库确认

物流或订舱人员
→ 主要查看航线、订舱、承运人状态和截止时间

关务人员
→ 主要查看单证、合规字段、申报准备和放行信息

管理人员
→ 查看整个案件的状态、异常、等待时间和审计记录
```

不同角色看到的操作不同，但底层不能复制三份订单。

## 3. 业务不是一条固定直线

错误理解是：

```text
供应链全部完成
→ 再订舱
→ 再准备关务
```

更真实的模型是：

```text
创建发运案件
        ↓
资料识别与字段核对
        ↓
 ┌────────────┬────────────┬────────────┐
 │ 初步装载规划 │ 提前订舱     │ 关务资料准备 │
 │ 可选、可跳过 │ 可并行推进   │ 可并行推进   │
 └────────────┴────────────┴────────────┘
        ↓
实际备货、装托和装箱
        ↓
最终箱数、重量、箱号、封志和 VGM 等事实
        ↓
各支线完成后进行装运前汇合检查
```

系统必须支持：

- 并行；
- 跳步；
- 补充资料；
- 人工覆盖；
- 等待外部系统；
- 网络失败后恢复；
- 从局部任务升级为完整案件。

它不能假设每一票货都必须运行 3D，也不能假设所有订舱都必须先有最终装载结果。

## 4. 不同运输场景怎样走不同路线

### 4.1 海运整柜

```text
文档受理
→ 初步装载和订舱准备并行
→ 人工确认订舱输入
→ LINK 提交
→ 实际装箱
→ 最终重量和 VGM
→ SI、关务和装运前检查
```

当前第 23 章只做到“箱到托盘”。托盘到集装箱、正式 VGM 和现场装箱反馈尚未实现，因此
现阶段不能宣称系统已经自动完成整柜装运。

### 4.2 海运拼箱

可以做箱到托盘规划，但最终拼柜可能由货代或集拼仓负责。案件路由允许跳过企业自己的
“托盘到集装箱”步骤。

### 4.3 空运和国际快递

跳过海运集装箱和 SOLAS VGM，保留包装尺寸重量核对、订舱或运单、商业单证、关务准备与
跟踪。

### 4.4 只做订舱

已有上游完整数据时，可以直接：

```text
创建轻量 Shipment Case
→ 绑定或创建 LINK 申请
→ 人工确认
→ 提交并等待结果
```

不强制先运行装载智能体。

### 4.5 只做装载规划

也允许：

```text
创建 Shipment Case
→ 绑定装载任务
→ 形成正式装载版本
→ 导出指导结果
→ 完成本次案件
```

不强制创建订舱申请。

## 5. Shipment Case 到底保存什么

第一阶段只把案件当成“跨服务关联和审计骨架”。

它保存：

```text
案件编号
案件名称
负责组织
运输场景
案件总生命周期状态
并发修订号
描述
外部业务资源绑定
案件审计事件
```

它不复制：

```text
装载任务的箱规
装载算法坐标
正式装载版本快照
LINK 订舱完整字段
承运人回调原始数据
```

这些数据继续由原业务服务负责。

第一阶段只保存稳定引用：

```text
LOAD_PLANNING_TASK + LP-DEMO-0001
LINK_BOOKING_APPLICATION + DEMO-BOOKING-0001
```

这叫“通过业务标识关联”，不是“跨数据库外键”。

## 6. 为什么统一进现有 Python Agent Runtime

第 23 章已经建立一个常驻 Python 进程：

```text
services/load-planning-service
端口：8200
Nacos 服务名：load-planning-service
数据库：load_planning_service
```

它已经具备 FastAPI、SQLAlchemy、Alembic、LangGraph、测试和 Nacos 注册。第 24 章会在同一
进程中增加 Shipment Case 模块，把这个进程逐步演进为统一的 TradeOps Agent Runtime。
一键启动脚本不会因此多启动一个 Python 服务。

第一阶段的职责划分是：

```text
Vue
→ Java platform-bff
  → 当前负责平台入口、服务发现、组织与菜单、DTO 适配和错误翻译
  → 后续负责登录 / Session、RBAC、可信服务身份和用户上下文传递
→ Python Agent Runtime
  → Shipment Case、资源绑定、案件事件、装载、未来 RAG 与 LangGraph 编排
→ Python LINK Service
  → 七步订舱、异步提交、幂等、重试和承运人回调
```

Shipment Case 的案件事实保存在 Python。Java BFF 后续只代理案件 API，不新增第二套 JPA
实体和案件表。这样可以让 Python 成为 Agent 领域逻辑的主要学习入口，也能避免 Java 与
Python 各保存一份案件状态。

资源绑定采用两种验证方式：

```text
装载任务
→ Agent Runtime 在自己的数据库内按 task_number 验证

LINK 订舱申请
→ Agent Runtime 直接调用 LINK 内部 HTTP API 验证
```

Python 不会绕回 Java 再访问 LINK，否则调用链会变成
`Java → Python Shipment Case → Java → Python LINK`，增加循环依赖和故障点。

现阶段暂不重命名 `load-planning-service` 的目录、Nacos 服务名、数据库和环境变量。这些
技术名称已经被启动脚本、Java 服务发现、测试、Alembic 和旧笔记引用。保留名称是兼容性
决策，不代表这个进程以后只负责装载。

总 Shipment LangGraph 会在案件模型和工具接口稳定后接入同一 Agent Runtime。第 24 章先
建立案件事实、并发控制和审计基础，不提前创建第三个常驻 Python 进程。

## 7. 第一阶段状态为什么故意很少

案件只使用：

```text
DRAFT
ACTIVE
COMPLETED
CANCELLED
```

合法转换：

```text
DRAFT → ACTIVE
ACTIVE → COMPLETED
DRAFT → CANCELLED
ACTIVE → CANCELLED
```

以下状态不能放进案件总状态：

```text
AWAITING_INPUT
PLAN_APPROVED
BOOKING_CONFIRMED
RETRY_WAIT
FAILED
```

原因是它们属于某个子任务。

例如 LINK 暂时投递失败，并不代表整票案件已经失败；案件可能仍在等待人工重试，装载和关务
支线也可能继续推进。

因此以后会出现：

```text
案件状态：ACTIVE
装载任务：LOCKED
订舱任务：RETRY_WAIT
关务任务：WAITING_DOCUMENT
```

而不是把所有信息压成一个越来越大的全局枚举。

## 8. LLM、LangGraph 和确定性代码分别负责什么

最终边界固定为：

```text
LLM
→ 理解自然语言、文档提取候选、总结、追问、工具选择和解释

LangGraph / Orchestrator
→ 安排步骤、条件分支、并行任务、等待、恢复、回退和人工节点

确定性服务
→ 重量、体积、坐标、状态机、事务、幂等、权限和正式提交

人工
→ 关键业务确认、安全责任、外部提交和例外处理
```

Shipment Case 不是聊天记录，也不是大模型记忆。它是数据库中的业务事实。

## 9. 安全、告警和运维放在哪里

它们必须做，但不能抢在核心业务闭环之前堆大量基础设施。

推荐顺序：

```text
第 24 章：Shipment Case、文档案件和合成数据
第 25 章：RAG、字段证据和跨文档核对
第 26 章：Shipment Orchestrator 和工具编排
第 27 章：企业案件工作台、E2E 和 Agent 评测
第 28 章：安全、权限、可观测、告警和运行治理
```

第 28 章必须包括：

- 真实登录和案件级权限；
- 工具白名单与强类型参数；
- Prompt Injection 和敏感信息测试；
- Trace、Metrics、日志和告警；
- 卡住运行、DEAD 投递和回调异常处理；
- 备份恢复和运行手册；
- 只读型 Ops Copilot。

第一版 Ops Copilot 只能读取脱敏后的状态、指标、Trace 和运行手册并给出建议，不能执行任意
Shell、SQL、部署、回滚或外部业务重放。

## 10. 本章结束后的产品变化

第 24 章完成后，系统应该从：

```text
关务入口 + 供应链入口 + 几个独立任务
```

变成：

```text
一票 Shipment Case
├── 有来源的文档和字段
├── 可选装载任务
├── 可选 LINK 订舱任务
├── 人工审批
├── 异常和等待
└── 一条完整时间线
```

这时第 21～23 章的代码不再是孤立练习，而会成为总 Agent 可以调用的专业工具。
