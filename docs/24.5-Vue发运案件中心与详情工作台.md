### 5.1 页面使用的主要类型

```ts
export type ShipmentCaseStatus =
  | 'DRAFT'
  | 'ACTIVE'
  | 'COMPLETED'
  | 'CANCELLED'
```

```ts
export type ShipmentResourceType =
  | 'LOAD_PLANNING_TASK'

```

```ts
export interface ShipmentCase {
  id: string
  caseNumber: string
  caseName: string
  responsibleOrganizationCode: string
  transportScenario: ShipmentTransportScenario
  status: ShipmentCaseStatus
  revision: number
  description: string | null
  createdAt: string
  updatedAt: string
  resourceBindings: ShipmentCaseResourceBinding[]
  events: ShipmentCaseEvent[]
}
```

TypeScript 类型解决的是开发期问题：

```text

状态和资源类型只能使用已知字符串
组件之间传递的数据形状明确
API 返回值在编辑器中可以自动提示
```

它不是服务端安全校验。浏览器请求仍可能被绕过，所以 Java 和 Python 会再次校验。

### 5.2 五个 API

| Vue 函数 | Java 平台接口 |
| --- | --- |
| `getShipmentCases()` | `GET /api/v1/platform/shipment-cases` |
| `getShipmentCase(caseNumber)` | `GET /api/v1/platform/shipment-cases/{caseNumber}` |
| `createShipmentCase(input, key)` | `POST /api/v1/platform/shipment-cases` |
| `bindShipmentCaseResource(caseNumber, input, key)` | `POST .../{caseNumber}/resources` |
| `changeShipmentCaseStatus(caseNumber, input, key)` | `POST .../{caseNumber}/status` |

所有写请求都把幂等键放在请求头：

```ts
headers: {
  'Content-Type': 'application/json',
  'Idempotency-Key': idempotencyKey,
}
```

案件编号在 URL 中使用：

```ts
encodeURIComponent(caseNumber)
```

页面不会自己拼接 Python 的 snake_case 请求。Vue 只使用 Java 平台的 camelCase 契约，
Java 再负责转换。

## 6. 为什么增加 `PlatformApiError`

原来的请求工具只抛出普通 `Error`。普通错误只有文字，没有 HTTP status：

```text
Error.message
```

Shipment Case 页面必须区分：

```text
普通输入错误
并发或状态冲突
后端暂时不可用
```

因此增加：

```ts
export class PlatformApiError extends Error {
  readonly status: number

  constructor(status: number, message: string) {
    super(message)
    this.name = 'PlatformApiError'
    this.status = status
  }
}
```

它仍然继承 `Error`，所以旧页面继续可以使用：

```ts
error instanceof Error
```

Shipment Case 页面则可以判断：

```ts
error instanceof PlatformApiError && error.status === 409
```

`requestWithOptions()` 负责：

```text
发送 fetch
-> 判断 HTTP 是否为 2xx
-> 选择接口专用中文错误
-> 尝试读取可用的服务端错误文字
-> 非 2xx 抛出 PlatformApiError
-> 2xx 拆开 ApiResponse<T>
-> 返回 result.data
```

Shipment Case 为 409 配置了接口专用文字，所以不会误用旧的全局提示：

```text
组织编码已存在，请更换编码
```





```text

```

之后 LINK 申请变成 `CONFIRMED`，案件绑定记录仍可能显示 `DRAFT`。它记录的是绑定证据，
不是实时同步结果。

```text

LINK_BOOKING_HTTP -> LINK 只读接口
```

### 9.5 资源绑定

用户选择资源类型并输入稳定业务编号。提交体是：

```ts
{
  resourceType,
  resourceNumber,
  expectedRevision: detail.value.revision,
}
```

页面只做编号格式校验。下面这些由 Python 判断：

```text
案件是否存在
资源是否存在
资源是否已经属于其他案件
案件当前状态能否继续绑定
expectedRevision 是否为最新值
```

绑定成功后，页面使用服务器返回的完整案件替换 `detail`，并把资源输入框清空。

### 9.6 生命周期操作

页面根据当前状态只展示可能的下一步：

```text
DRAFT -> ACTIVE 或 CANCELLED
ACTIVE -> COMPLETED 或 CANCELLED
COMPLETED -> 无按钮
CANCELLED -> 无按钮
```

这是前端体验控制，不是最终状态机。Python 会再次校验状态转换。

每次状态变化必须填写原因。提交体：

```ts
{
  targetStatus,
  expectedRevision: detail.value.revision,
  reason,
}
```

进入 `COMPLETED` 或 `CANCELLED` 后，详情页显示只读终态提示，不再显示资源绑定表单和状态按钮。

### 9.7 审计时间线

详情页把事件按 `sequence` 从大到小显示：

```ts
[...(detail.value?.events ?? [])]
  .sort((left, right) => right.sequence - left.sequence)
```

每条事件显示：

```text
sequence
事件类型
发生时间
资源类型
事件说明
actor
requestId
```

当前已知事件会翻译成：

```text
CASE_CREATED -> 创建案件
RESOURCE_BOUND -> 绑定专业资源
CASE_STATUS_CHANGED -> 案件状态变更
```

未知的新事件类型仍可显示原始字符串，不会让整个页面无法渲染。

## 10. 前端幂等键到底怎样管理

三个写操作都通过同一个 helper 管理待确认命令：

```text
platform-web/src/components/shipment-case/
shipmentCasePendingCommands.ts
```

浏览器存储命名空间：

```text
customs-affairs-os.shipment-case.pending-commands.v1
```

收口审查时发现，最初版本只把 key 放在组件 `ref` 中。网络失败后如果刷新页面或关闭再打开
抽屉，浏览器会忘记原 key。现在改为 `sessionStorage`，因此同一个标签页刷新后仍能恢复；
关闭整个标签页会结束这段会话状态。

### 10.1 一条待确认命令保存什么

每条记录保存：

```ts
{
  commandType: 'CREATE_CASE' | 'BIND_RESOURCE' | 'CHANGE_STATUS'
  scope: string
  fingerprint: string
  key: string
  updatedAt: number
}
```

记录不是只按 fingerprint 全局查找，而是先按“命令类型 + 作用范围”定位：

```text
CREATE_CASE + create-form
BIND_RESOURCE + caseNumber
CHANGE_STATUS + caseNumber
```

这样案件 A 的资源绑定不会覆盖案件 B 的资源绑定，资源绑定也不会覆盖同一案件的状态命令。

### 10.2 fingerprint 是什么

页面先生成真正要提交的输入：

```ts
const input = {
  targetStatus: selectedTargetStatus.value,
  expectedRevision: detail.value.revision,
  reason,
}
```

再计算：

```ts
const fingerprint = JSON.stringify(input)
```

fingerprint 相同表示：

```text
用户正在重试同一份命令内容
```

fingerprint 不同表示：

```text
字段、原因或 expectedRevision 已经改变
```

这里的 fingerprint 不是密码学哈希，而是规范化请求对象的 JSON 字符串。它既用于判断请求
内容是否相同，也能在抽屉重新打开时恢复待确认表单。

### 10.3 key 怎样生成

创建命令：

```text
shipment-case-create-{UUID}
```

资源绑定：

```text
shipment-resource-bind-{UUID}
```

状态变化：

```text
shipment-status-change-{UUID}
```

UUID 由浏览器的：

```ts
crypto.randomUUID()
```

生成。

`getOrCreateShipmentCaseCommandKey()` 的判断是：

```text
commandType 相同
+ scope 相同
+ fingerprint 相同
-> 返回原 key
```

如果同一命令类型和 scope 下的 fingerprint 已经变化，helper 会用新 key 和新记录替换旧记录。

### 10.4 什么时候复用原 key

这些情况保留并复用原 key：

```text
fetch 没有拿到 HTTP 响应
HTTP 5xx
HTTP 502 或 503
用户关闭抽屉，但没有明确放弃待确认命令
同一标签页刷新后，案件 revision 仍与原命令一致
```

创建抽屉重新打开时，会从 fingerprint 恢复案件编号、案件名称、运输场景和业务说明。

详情抽屉重新打开时，会先 GET 最新案件。只有原命令的 `expectedRevision` 仍等于最新
revision，页面才恢复资源绑定或状态表单。若 revision 已变化，旧命令已经不再建立在用户
当前看到的案件版本上，页面会清除它。

假设 Python 已经写成功，但响应在网络中丢失。创建命令再次携带同一个 key，Python 可以
返回第一次命令的已有结果，不会重复创建案件或事件。详情命令如果已经成功，重新 GET 通常
会看到 revision 已推进，此时旧的待确认记录会被清理。

### 10.5 什么时候产生新 key

下一次提交时，只要规范化请求发生变化，就会生成新 key。

例如：

```text
修改案件名称
修改资源编号
修改状态变化原因
冲突刷新后 expectedRevision 改变
```

组件还会在真实的用户输入事件发生时立即清除旧记录。恢复待确认表单后，只要用户修改任一
字段，即使最后又手工改回原文字，也会被视为重新确认过的新命令。

### 10.6 什么时候主动丢弃旧 key

当前代码的真实规则如下。

| 场景 | 处理 |
| --- | --- |
| 写入成功并收到响应 | 清除与本次 fingerprint 匹配的记录。 |
| HTTP 400 | 已得到确定拒绝，清除本次记录；用户修正后形成新命令。 |
| HTTP 409 | 清除该案件的旧资源/状态命令，再刷新权威详情，不自动重放。 |
| 用户修改任一真实字段 | 立即清除对应记录；下次提交生成新 key。 |
| 创建表单点击“重置” | 清除创建记录并清空字段。 |
| 状态表单点击“返回”或重新选择目标 | 清除原状态记录。 |
| 关闭抽屉 | 不清除结果尚未确认的记录。 |
| 网络错误或 5xx | 保留记录，未修改表单时可以安全重试。 |

清理函数可以同时接收 fingerprint。成功响应和 HTTP 400 会只删除仍与本次请求匹配的记录，
避免未来页面出现并行交互时误删一条较新的命令。

当前代码对 404 不会主动清除待确认记录。再次提交相同内容时仍会复用原 key；用户修改字段、
重置表单、结束标签页会话或记录过期后，旧记录会被清理。

### 10.7 怎样避免 sessionStorage 一直增长

helper 同时使用两道边界：

```text
TTL：6 小时
数量上限：24 条
```

每次读取和写入都会删除过期记录，再只保留更新时间最新的 24 条。浏览器禁用
`sessionStorage` 时，代码会退化到当前页面内存，不会因为技术存储不可用而阻断表单。

边界要说清楚：

```text
同一标签页关闭/重开抽屉：可以恢复
同一标签页刷新页面：可以恢复
新开另一个标签页：项目不支持跨标签页恢复
关闭标签页后重新开页面：项目不保证进入新的浏览器会话后仍能恢复
另一台设备：项目不支持恢复
```

这不是后端命令队列，也不是跨设备恢复机制。Python 保存的幂等事实仍是最终安全边界；
`sessionStorage` 只是帮助浏览器在结果不明确时找回应当重用的 key。

## 11. revision 和 409 冲突怎样处理

### 11.1 revision 解决什么问题

假设两个标签页同时打开同一案件：

```text
标签页 A 看到 R3
标签页 B 也看到 R3
```

A 先完成一次写入：

```text
A 提交 expectedRevision=3
-> 成功
-> 案件变成 R4
```

B 仍拿旧值提交：

```text
B 提交 expectedRevision=3
-> Python 发现当前已经是 R4
-> HTTP 409
```

如果没有 revision，B 可能把基于旧信息作出的决定覆盖到新状态上。

### 11.2 为什么 409 不自动重放

收到 409 后，页面不会把旧命令改成新 revision 并自动再发一次。

原因是：

```text
案件事实已经变化
旧的业务判断可能已经不成立
状态目标可能不再合法
资源可能已经被绑定
```

自动重放会把一次技术重试变成未经用户确认的新业务决定。

### 11.3 当前 409 处理顺序

`refreshAfterConflict()` 执行：

```text
清除资源命令 key
-> 清除状态命令 key
-> 显示冲突提示
-> GET 最新案件详情
-> 用最新快照替换 detail
-> 同步父列表
-> 检查原状态目标是否仍然合法
-> 不合法时清除目标和原因
-> 等待用户重新确认
```

提示文字会说明：

```text
已刷新案件最新版本，请确认后重新操作
```

用户再次提交时，命令会带新的 revision 和新的 key。

### 11.4 幂等和乐观并发不是同一个功能

```text
Idempotency-Key
-> 防止同一条命令因为重试被执行两次

expectedRevision
-> 防止基于旧案件快照执行新命令
```

两者必须同时存在：

```text
同一命令重试
-> 相同 key + 相同 expectedRevision

冲突后用户重新确认
-> 新 key + 最新 expectedRevision
```

当前项目没有安装 Vitest、Jest 或 Playwright。本节用浏览器开发者工具验证

2. 打开浏览器开发者工具，把 Network 临时切换为 `Offline`。
3. 点击“创建案件”。请求会失败，但页面会先保存待确认命令。
4. 在 Application -> Session Storage 中找到：

   ```text
   customs-affairs-os.shipment-case.pending-commands.v1
   ```

5. 记录其中 `CREATE_CASE::create-form` 的 `key`。
6. 恢复 `Online`，刷新当前标签页，再打开创建抽屉。
7. 预期表单自动恢复，并显示“已恢复上次结果尚未确认的创建命令”。

1. 用 `Offline` 再制造一条待确认创建命令。

3. 修改案件名称中的任意一个字符。
4. 预期存储中的旧创建记录立即消失。

```text

详情重新打开后会先 GET 最新案件

```

还应补充检查确定响应的清理：


这个测试只能证明当前标签页的恢复和清理规则。项目没有实现跨标签页、浏览器会话或设备的
待确认 key 恢复，不能把 `sessionStorage` 写成跨端命令队列。

```text
R1 创建
R2 并发赢家绑定装载或 LINK
R3 刷新后完成另一资源绑定
R4 激活
R5 完成
```

最终有 5 条业务事件和 6 条成功命令记录。第 6 条是重复绑定产生的 `NO_OP`；它占用
`Idempotency-Key`，但不推进 revision，也不新增业务事件。创建重放、状态重放、并发
loser 和故意制造的 409 同样没有占用新的 revision。
