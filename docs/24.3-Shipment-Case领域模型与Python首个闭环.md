## 3. 四张表分别保存什么

### 3.1 `shipment_cases`

一行表示一票发运案件。

| 字段 | 含义 |
| --- | --- |
| `id` | UUID 技术主键。 |
| `case_number` | 稳定业务编号，唯一。 |
| `case_name` | 页面显示名称。 |
| `responsible_organization_code` | 当前由服务端写入 `DEMO_ORG`。 |
| `transport_scenario` | 运输场景。 |
| `status` | 案件总生命周期状态。 |
| `revision` | 乐观并发修订号。 |
| `description` | 可选业务说明。 |
| `created_at` | 创建时间。 |
| `updated_at` | 最近修改时间。 |

页面和跨服务接口应优先使用：

```text
case_number
```

UUID `id` 适合数据库关系和技术排查，不应代替业务编号。

### 3.2 `shipment_case_resource_bindings`

一行表示案件绑定了一个外部业务资源。

| 字段 | 含义 |
| --- | --- |
| `case_id` | 只外键到 `shipment_cases.id`。 |
| `resource_type` | 装载任务或 LINK 申请。 |
| `resource_number` | 对应系统的稳定业务编号。 |
| `resource_status_at_verification` | 绑定时观察到的状态快照。 |
| `verification_source` | 使用哪个验证器确认。 |
| `verified_at` | 验证发生时间。 |
| `bound_at` | 绑定写入时间。 |

数据库约束：

```text
UNIQUE(resource_type, resource_number)
```

因此同一个装载任务或 LINK 申请不能属于两个案件。

绑定表没有这些外键：

```text
resource_number -> load_planning_tasks
resource_number -> LINK booking_applications
```

即使装载任务当前和 Shipment Case 共用一个数据库，也只保存业务编号。以后拆分进程或数据库
时，不需要删除跨模块外键。

### 3.3 `shipment_case_events`

事件表只追加，不提供业务更新或删除入口。

| 字段 | 含义 |
| --- | --- |
| `sequence` | 案件内事件顺序。 |
| `event_type` | `CASE_CREATED`、`RESOURCE_BOUND` 或 `CASE_STATUS_CHANGED`。 |
| `previous_status` | 状态变化前的值。 |
| `current_status` | 状态变化后的值。 |
| `resource_type` | 资源事件对应的类型。 |
| `resource_number` | 资源事件对应的编号。 |
| `actor_*` | 当前由服务端写入 `SYSTEM_DEMO` 演示占位身份；浏览器无法伪造，但它不是已认证用户。 |
| `request_id` | 当前由 Python 为该事件生成的关联 UUID；尚未贯通 Java Request ID 或 Trace。 |
| `detail` | 人工可读的事件说明。 |
| `occurred_at` | 事件时间。 |

事件表只保证业务事件顺序：

```text
同一案件不能出现重复 sequence
```

当前实现还保持：

```text
event.sequence == shipment_case.revision
```

创建案件时两者都从 1 开始。每个有效资源绑定或状态变化让 revision 增加 1，并追加一条同
序号事件。

### 3.4 `shipment_case_commands`

命令台账记录每一个服务端已经成功完成并提交的写命令。即使 HTTP 响应随后在网络中丢失，
命令记录也已经存在，调用方才能用相同 key 安全恢复结果：

| 字段 | 含义 |
| --- | --- |
| `case_id` | 命令所属案件。 |
| `command_type` | `CREATE_CASE`、`BIND_RESOURCE` 或 `CHANGE_STATUS`。 |
| `idempotency_key_hash` | 原始 `Idempotency-Key` 的 SHA-256，全表唯一。 |
| `request_hash` | 规范化 payload 的 SHA-256。 |
| `request_id` | 本次首次成功执行的服务端关联 UUID。 |
| `result_kind` | `APPLIED` 或 `NO_OP`。 |
| `result_revision` | 首次成功响应对应的案件 revision。 |
| `result_event_id` | `APPLIED` 对应的业务事件；`NO_OP` 必须为空。 |
| `completed_at` | 命令首次成功完成时间。 |

这里要分清两个问题：

```text
shipment_case_commands
回答：这个 HTTP 命令是否已经成功，能否安全重放？

shipment_case_events
回答：案件真正发生了什么业务事实？
```

重复绑定同一个已经属于本案件的资源会成功返回，但不会产生新业务事实。因此它只新增：

```text
result_kind = NO_OP
```

不会新增第二条 `RESOURCE_BOUND`，也不会推进 revision。即便如此，这个 key 已经得到过
成功响应，之后换 payload 复用时仍必须返回 409。

`APPLIED` 命令的 `result_event_id` 使用 `ON DELETE RESTRICT` 指向事件表。这样误删一条
业务事件时，数据库不会连带删除命令记录并释放已经用过的 key。ORM 的事件关系也没有
`delete-orphan`；当前 API 不提供事件删除入口。

## 4. 枚举为什么这样设计

### 4.1 案件状态

```text
DRAFT
ACTIVE
COMPLETED
CANCELLED
```

合法转换：

```text
DRAFT -> ACTIVE
DRAFT -> CANCELLED
ACTIVE -> COMPLETED
ACTIVE -> CANCELLED
```

`COMPLETED` 和 `CANCELLED` 是终态。

案件状态没有加入：

```text
AWAITING_INPUT
READY_FOR_REVIEW
RETRY_WAIT
BOOKING_CONFIRMED
```

这些状态属于装载运行或订舱申请。案件可以保持 `ACTIVE`，同时某条子任务等待人工或网络
恢复。

### 4.2 运输场景

```text
UNDECIDED
SEA_FCL
SEA_LCL
AIR
EXPRESS
LOAD_PLANNING_ONLY
BOOKING_ONLY
```

`UNDECIDED` 允许系统在运输场景尚未确认时先建立 DRAFT 案件。例如 Packing List 和
Commercial Invoice 已经发现冲突，但业务人员还没有确认走海运还是空运。

### 4.3 资源类型

```text
LOAD_PLANNING_TASK
LINK_BOOKING_APPLICATION
```

第一阶段只接入已经存在并有稳定编号的两个资源。未来增加关务准备任务时，应新增明确枚举
和验证器，不能把任意 URL 或表名写进 `resource_type`。

## 6. 幂等到底怎样工作

### 6.1 原始 key 不落库

HTTP 请求头可能是：

```text
create-shp-demo-fcl-001
```

数据库保存：

```text
SHA-256(key)
```

源码、响应、命令台账和事件都不会返回原始 key。

### 6.2 key 和请求内容必须同时一致

系统还会把规范化命令转换成 `request_hash`：

```text
action
业务字段
expected_revision
```

相同 key 和相同请求会命中 `shipment_case_commands`：

```text
返回已有案件
不增加 revision
不追加事件
```

相同 key 换参数：

```text
HTTP 409
```

这可以发现客户端错误地复用幂等键。

### 6.3 为什么幂等检查早于 revision

假设第一次绑定已经成功：

```text
请求携带 expected_revision=1
-> 数据库变成 revision=2
-> 返回响应时网络中断
```

浏览器重试的请求仍然携带：

```text
expected_revision=1
```

如果先检查 revision，系统会错误返回 409。当前代码先查询命令台账：

```text
命中相同 key 和 request_hash
-> 返回当前案件
-> 不再检查旧 revision
-> 不再次调用 LINK
```

这才是网络重试需要的行为。

### 6.4 为什么成功 no-op 也必须登记

假设资源已经属于案件，页面换一个新 key 再次绑定：

```text
业务结果已经成立
-> 返回 200
-> revision 不变
-> 不追加 RESOURCE_BOUND
```

虽然它没有新事件，但调用方已经得到成功响应。系统必须写入一条 `NO_OP` 命令记录。否则
同一个 key 随后换成另一资源时，数据库找不到过去的成功结果，就会错误接受第二份 payload。

因此：

```text
成功命令数可以大于业务事件数
```

这不是审计遗漏，而是命令结果和领域事实本来就不完全一一对应。

## 7. revision 解决什么问题

两个浏览器窗口可能同时读取：

```text
revision=1
```

窗口 A 先绑定装载任务：

```text
revision 1 -> 2
```

窗口 B 仍想用 `expected_revision=1` 绑定另一资源：

```text
HTTP 409
当前 revision=2
```

用户刷新详情后，再基于 revision 2 发新命令。

数据库行锁负责串行化同一时刻的写入，`expected_revision` 负责告诉用户旧页面已经过期。两者
用途不同，不能只保留其中一个。

## 8. 资源绑定为什么分三段

### 8.1 阶段 A：短锁行事务

Service 打开第一段事务并锁住案件主行：

```text
SELECT 案件 FOR UPDATE
-> 查询相同幂等命令
-> 查询资源是否已经绑定
-> 已属于本案件时登记 NO_OP 命令
-> 检查案件是否为终态
-> 提交并关闭事务
```

如果同一个命令已经成功，阶段 A 直接返回。LINK 后来即使停机，也不会把过去已经成功的
绑定误报成失败。阶段 A 不只是读取：同案重复绑定时，它会在这个短事务中写入成功
`NO_OP`。事务结束后才进入阶段 B，因此等待 LINK 时仍不持有案件行锁或数据库事务。

### 8.2 阶段 B：没有案件数据库事务

Service 调用资源验证器：

```text
LOAD_PLANNING_TASK
-> 查询本地 load_planning_tasks

LINK_BOOKING_APPLICATION
-> GET LINK /api/v1/booking-applications/{application_number}
```

LINK 超时期间没有锁住 `shipment_cases` 行。

### 8.3 阶段 C：短写事务

远程验证结束后，Service 新建会话：

```text
SELECT shipment_case FOR UPDATE
-> 再查一次幂等命令
-> 再查一次资源唯一绑定
-> 并发期间已绑定到本案件时登记 NO_OP
-> 再检查终态
-> 检查 expected_revision
-> revision + 1
-> 写 binding
-> 写 event
-> 写 APPLIED command
-> 一次提交
```

阶段 C 必须重复检查。阶段 B 等待 HTTP 时，另一个请求可能已经修改案件或抢先绑定同一资源。

## 10. HTTP 错误语义

| 场景 | 状态码 |
| --- | --- |
| 案件不存在 | 404 |
| 引用的装载任务或 LINK 申请不存在 | 422 |
| 幂等 key 换参数 | 409 |
| revision 已过期 | 409 |
| 资源已经属于另一案件 | 409 |
| 非法状态转换 | 409 |
| LINK 超时、连接失败或 5xx | 503 |
| LINK 返回错误 JSON、编号不一致或缺字段 | 502 |
| 请求体多传 actor 或组织 | 422 |

资源不存在使用 422，是因为当前案件 URL 有效，错误发生在命令引用的业务资源。LINK 服务暂时
不可用使用 503，调用方可以用同一幂等 key 稍后重试。

## 11. 并发时为什么还要依赖数据库唯一约束

应用层会先查询：

```text
资源是否已经绑定
```

两个请求仍可能同时得到：

```text
没有绑定
```

最终防线是数据库：

```text
UNIQUE(resource_type, resource_number)
```

失败请求回滚后重新查询：

```text
同一案件已经得到该资源
-> 写入自己的 NO_OP 命令结果
-> 按业务成功返回，但不新增 RESOURCE_BOUND

另一案件得到该资源
-> 返回 409
```

`shipment_case_commands.idempotency_key_hash` 也有全局唯一约束。两个相同 key 的请求同时
提交时，数据库决定唯一赢家；loser 回滚后读取赢家的命令记录：

```text
同 action + 同 request_hash + 同 case
-> 幂等重放成功

任一项不同
-> HTTP 409
```

这说明“先查再写”不能代替唯一约束。应用校验提供清晰错误，数据库约束裁决并发。

`downgrade 02 -> 01` 只能把 `APPLIED` 命令还原回旧事件字段。旧结构没有位置保存
`NO_OP`，因此生产回滚前必须明确接受这部分命令台账会丢失，不能把 downgrade 当成无损操作。

## 16. 这一版尚未完成什么

当前 Python 首个闭环已经能：


还没有：

```text

```

因此这一节完成的是 Python 领域底座，不代表整个 TradeOps Agent 已经结束。
