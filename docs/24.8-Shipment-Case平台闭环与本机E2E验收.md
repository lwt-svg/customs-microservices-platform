## 2. 为什么单元测试通过后还需要 E2E

不同层的测试解决不同问题。

| 测试层次 | 主要证明什么 | 不能单独证明什么 |
| --- | --- | --- |
| Python 领域测试 | 状态机、Repository、幂等和并发规则正确 | Java 是否能找到 Python |
| Java Controller 测试 | 路由、参数校验、HTTP 外壳正确 | 真实 Nacos 和 Python 是否可用 |
| Java Service 测试 | DTO 转换、错误翻译、请求头透传正确 | 真实 MySQL 表是否已经迁移 |
| Vue type-check/build | TypeScript 类型和前端构建通过 | 浏览器请求是否能完成真实写库 |
| 本节 E2E | 各层通过真实网络和数据库连成闭环 | 浏览器视觉效果和生产环境可靠性 |

例如，下面这些问题可能在单元测试全部通过时仍然出现：

```text
Java 使用了错误的 Nacos 服务名
Python 已注册，但注册地址或端口错误
Java camelCase 到 Python snake_case 的真实请求不匹配
Flyway 或 Alembic 没有在真实 MySQL 执行
Java 转发时漏掉 Idempotency-Key
绑定 LINK 时，Python 无法访问 LINK 服务
前后端看到的 revision 与数据库事实不一致
```

所以 E2E 不是重复测试，而是验证模块之间的接缝。

## 3. 脚本为什么只访问 Java 8080

脚本固定入口是：

```python
BASE_URL = "http://127.0.0.1:8080"
```

它只允许访问：

```text
/api/v1/platform/*
```

脚本不会直接请求：

```text
http://127.0.0.1:8200
http://127.0.0.1:8000
http://127.0.0.1:8848
MySQL 3306
```

这项限制非常重要。

如果验收脚本直接调用 Python 8200，即使成功，也只能证明 Python 接口可用，不能证明：

```text
Java 路由存在
Java 能从 Nacos 找到 Python
Java 请求和响应 DTO 转换正确
Java 能保留 201、400、404、409、502、503 等错误语义
Java 正确透传 Idempotency-Key
```

现在脚本只请求 8080，成功时实际覆盖的是：

```text
shipment-case-e2e.py
        |
        v
Java BFF :8080
        |
        +-- 通过 Nacos 找到 LINK Python :8000
        |
        +-- 通过 Nacos 找到 Agent Runtime :8200
                                      |
                                      +-- 查询本地装载数据库
                                      |
                                      +-- 通过只读 HTTP 验证 LINK 申请
                                      |
                                      +-- 读写 Shipment Case 四张表
```

脚本还做了两项保护：

1. `BffClient` 会拒绝 `/api/v1/platform/` 之外的路径。
2. `NoRedirectHandler` 会拒绝 HTTP 重定向，避免请求被悄悄带离固定的本机 8080。

正式写入数据前，`probe_platform()` 会先通过 Java 读取三条核心平台链路：

| 平台读取接口 | 实际验证重点 |
| --- | --- |
| `GET /api/v1/platform/load-planning/tasks` | Java → 智能装载 Python → MySQL |
| `GET /api/v1/platform/link-booking/applications` | Java → LINK Python → MySQL |
| `GET /api/v1/platform/shipment-cases` | Java → Shipment Case Python → MySQL |

三次返回的 `data` 都必须是数组，脚本才会进入后续写入验收。

因此，这是一项从平台入口观察系统的黑盒验收，不是绕过 Java 直接验证 Python。

## 4. 启动前要知道的两个数据库归属

本项目同时出现 Flyway 和 Alembic，不是同一张表被迁移两次。

| 服务 | 迁移工具 | MySQL schema | 本节相关内容 |
| --- | --- | --- | --- |
| Java BFF | Flyway | `platform_bff_lab` | V9 菜单数据 |
| Python Agent Runtime | Alembic | `load_planning_service` | Shipment Case 领域表 |

Java V9 文件是：

```text
platform-bff/src/main/resources/db/migration/
V9__seed_shipment_case_menu.sql
```

它只增加：

```text
TradeOps
└── 发运案件中心
```

它不会创建 Shipment Case 业务表。

Python Alembic 文件是：

```text
services/load-planning-service/alembic/versions/
20261015_01_create_shipment_case_tables.py
20261015_02_add_shipment_case_command_ledger.py
```

两次迁移按开发顺序完成：

```text
20261015_01
-> 创建 shipment_cases
-> 创建 shipment_case_resource_bindings
-> 创建 shipment_case_events

20261015_02
-> 回填历史已成功命令
-> 创建 shipment_case_commands
-> 把 HTTP 幂等结果与业务事件分开
```

02 会在执行任何 DDL 前检查未知事件类型和历史重复 key，避免 MySQL 非事务 DDL 在预检失败
后留下半迁移结构。`APPLIED` 命令到事件的外键使用 `ON DELETE RESTRICT`，防止误删事件后
释放已经使用过的 key。

`downgrade 02 -> 01` 不是无损回滚。旧结构无法保存 `NO_OP` 命令，因此生产环境若要降级，
必须先评估并接受这部分命令台账会丢失。

这反映了数据库所有权：

```text
平台菜单属于 Java 平台数据库
Shipment Case 业务事实属于 Python Agent Runtime 数据库
```

### 5.3 为什么先创建专业资源

Shipment Case 不复制装载任务和订舱申请的完整业务明细，只保存稳定编号和验证快照。

因此绑定前必须先存在：

```text
一个真实写入本机数据库的装载任务
一个真实写入本机数据库的 LINK 草稿
```

如果脚本只伪造两个编号，当前 Java 平台接口会返回 HTTP 400，不能算闭环成功。Python
内部接口先把“资源不存在”表示为 422，Java 再归一成平台 400；案件编号本身不存在才是
平台 404。

## 6. 前置资源没有幂等键时怎样避免重复

当前装载任务创建和 LINK 草稿创建接口还没有请求级 `Idempotency-Key`。

假设客户端发送 POST 后网络中断，会出现一种危险情况：

```text
服务端可能已经写库
客户端却没有收到响应
```

这时盲目重发 POST 可能重复创建。

脚本的处理方式是：

```text
第一次 POST
-> 如果得到明确 HTTP 结果，按结果继续
-> 如果网络结果未知，只按稳定业务编号执行 GET
-> GET 能找到就恢复权威结果
-> GET 仍找不到就停止，绝不自动重发 POST
```

对应代码：

```text
create_load_task_or_recover()
create_link_draft_or_recover()
recover_non_idempotent_create()
```

这里的学习重点是：

```text
“重试”不是见到异常就再发一次。
是否能重试，取决于命令是否具备幂等保护，以及结果究竟是未知还是明确失败。
```

## 7. Shipment Case 的 11 步真实闭环

脚本的主流程在：

```python
run_e2e()
```

完整顺序如下。

| 步骤 | 操作 | 预期结果 |
| --- | --- | --- |
| 1 | 创建合成装载任务 | 得到真实任务编号和状态 |
| 2 | 创建 LINK 合成草稿 | 状态为 `DRAFT` |
| 3 | 创建 Shipment Case | 状态 `DRAFT`，`revision=1` |
| 4 | 使用相同 key 重放创建命令 | 同一 id，revision 仍为 1 |
| 5 | 两个线程用同一 revision 并发绑定装载与 LINK | 必须恰好一条成功、一条 409；案件只进入 `revision=2` |
| 6 | 用最新 revision 完成 loser 绑定，再验证成功 `NO_OP` | 进入 `revision=3`；`NO_OP` 不推进 revision，其 key 换 payload 必须 409 |
| 7 | 故意用旧 revision 激活 | 必须返回 HTTP 409 |
| 8 | 使用当前 revision 激活 | 状态 `ACTIVE`，`revision=4` |
| 9 | 使用相同 key 重放激活 | revision 仍为 4，不增加事件 |
| 10 | 完成案件 | 状态 `COMPLETED`，`revision=5` |
| 11 | GET 最终详情 | 复核绑定、快照、revision 和事件 |

下面分别解释最重要的业务保证。

## 8. 创建命令的幂等重放

创建 Shipment Case 时，脚本先生成一个固定 key：

```python
create_key = f"shipment-case-e2e-create-{uuid.uuid4()}"
```

第一次请求使用：

```text
相同业务 payload
固定 Idempotency-Key
```

成功后应得到：

```text
status = DRAFT
revision = 1
一条 CASE_CREATED 事件
```

第 4 步故意再次发送完全相同的 payload 和完全相同的 key。

重放结果必须满足：

```text
案件 id 不变
caseNumber 不变
revision 仍为 1
不创建第二条案件
不增加第二条 CASE_CREATED 事件
```

这说明“客户端没有收到响应，重试同一条命令”不会重复产生业务事实。

### 8.1 哪些情况脚本会自动重试

`post_idempotent_case_command()` 只在以下异常时自动重试：

```text
NetworkOutcomeUnknown
```

而且每次重试都复用原来的 `Idempotency-Key`。

下面这些明确 HTTP 结果不会被脚本自动重放：

```text
400
404
409
5xx
```

这是当前脚本的保守策略：只有“没有取得完整 HTTP 结果”的同一命令才自动重试。服务端
已经明确给出状态码时，交给上层判断，不能把业务冲突当成普通网络抖动。

## 9. 两类资源绑定与“绑定时状态快照”

绑定装载任务时，Agent Runtime 直接查询自己的本地数据库。

保存的验证来源是：

```text
LOCAL_LOAD_PLANNING_DATABASE
```

绑定 LINK 申请时，Agent Runtime 调用 LINK 的只读 HTTP 接口。

保存的验证来源是：

```text
LINK_BOOKING_HTTP
```

每条绑定还保存：

```text
resourceStatusAtVerification
verifiedAt
boundAt
```

本次两个资源在绑定时都是 `DRAFT`。

### 9.1 快照不等于实时状态

假设 LINK 申请绑定时是 `DRAFT`，后来在 LINK 工作台变成 `SUBMITTED`。

Shipment Case 中原有绑定仍会显示：

```text
绑定时状态快照：DRAFT
```

这是有意设计，不是同步失败。

快照回答的问题是：

```text
“案件当时依据什么状态完成了资源绑定？”
```

它不回答：

```text
“源系统此刻的最新状态是什么？”
```

查看最新状态仍应进入对应专业工作台。后续若要增加实时聚合，应新增显式查询能力，不能
偷偷改写历史验证快照。

### 9.2 为什么第 5 步必须真正并发

第 5 步使用 `ThreadPoolExecutor` 同时发送两条资源绑定命令：

```text
绑定装载任务：expectedRevision=1，独立 Idempotency-Key
绑定 LINK 草稿：expectedRevision=1，独立 Idempotency-Key
```

哪一条先成功不固定。脚本只要求：

```text
恰好一条返回成功
恰好一条返回 409
数据库只新增一条绑定和一条 RESOURCE_BOUND
案件从 R1 精确进入 R2
```

随后脚本读取最新案件，把失败命令的 `expectedRevision` 改成 2，并使用新的 key 由调用方
明确重试。第二条资源真正绑定后，案件才进入 R3。

第 6 步还用另一个新 key 重复绑定已经属于本案件的资源。服务端返回成功并写入：

```text
shipment_case_commands.result_kind = NO_OP
```

这条命令不会新增 `RESOURCE_BOUND`，也不会推进 revision。脚本随后故意用同一个
`NO_OP` key 改绑另一资源，必须得到 409。这样才能证明“成功但没有改变业务事实”的命令
也被可靠占用，不能换 payload 二次使用。

## 10. 为什么旧 revision 必须返回 409

完成两个资源绑定后，案件当前 revision 已经是 3。

第 7 步故意提交第 5 步并发赢家完成后看到的旧 revision 2。并发赢家可能是装载，也可能是
LINK，因此这里不能把 revision 2 写成某一种固定资源的绑定结果：

```json
{
  "targetStatus": "ACTIVE",
  "expectedRevision": 2,
  "reason": "E2E 故意提交旧 revision，验证乐观并发保护。"
}
```

服务端必须返回：

```text
HTTP 409 Conflict
```

脚本随后重新 GET 案件，并断言：

```text
案件仍为 DRAFT
revision 仍为 3
事件仍只有 3 条
```

也就是说，冲突命令没有产生半成功数据。

### 10.1 409 为什么不能自动重试

409 是服务端给出的明确业务结果：

```text
你提交命令时依据的案件版本已经过期。
```

如果客户端悄悄换成最新 revision 再自动提交，相当于替用户做了一个新的业务决定。

正确流程是：

```text
收到 409
-> 丢弃旧命令的幂等 key
-> GET 最新案件
-> 向用户展示最新 revision 和业务事实
-> 用户确认后，生成新 key，提交一条新命令
```

自动脚本只确认冲突保护有效，不会替用户自动重放。

Vue 详情抽屉也采用相同原则：

```text
收到 409 后自动刷新读取
不自动再次执行写操作
保留可读提示
等待用户重新确认
```

## 11. revision 与事件 sequence 怎样对应

本次真正改变案件事实的命令只有五条：

| 成功变更 | revision | 新事件 sequence | 事件类型 |
| --- | ---: | ---: | --- |
| 创建案件 | 1 | 1 | `CASE_CREATED` |
| 并发绑定中的赢家（装载或 LINK） | 2 | 2 | `RESOURCE_BOUND` |
| 刷新后明确重试的 loser（另一资源） | 3 | 3 | `RESOURCE_BOUND` |
| `DRAFT → ACTIVE` | 4 | 4 | `CASE_STATUS_CHANGED` |
| `ACTIVE → COMPLETED` | 5 | 5 | `CASE_STATUS_CHANGED` |

本次还有多条请求不能推进 revision：

```text
创建命令幂等重放
并发绑定中的 loser 409
同资源重复绑定的成功 NO_OP
NO_OP key 换 payload 后的 409
旧 revision 导致的 409
ACTIVE 命令幂等重放
```

最终断言包括：

```text
成功变更 revision 精确等于 [1, 2, 3, 4, 5]
五个 revision 不重复
事件总数精确等于 5
事件 sequence 精确等于 [1, 2, 3, 4, 5]
事件 sequence 不重复
最终 revision 等于最后一条事件 sequence
成功命令台账精确等于 6 条，其中 5 条 APPLIED、1 条 NO_OP
```

这能发现常见错误：

```text
幂等重放又写了一条事件
409 冲突错误地占用了 revision
主表更新成功但事件漏写
事件写入成功但主表 revision 没推进
并发下出现重复 sequence
```

## 16. 失败时怎样排查

先不要反复运行 E2E。先确认失败属于哪一层。

### 16.1 平台链路未就绪

现象：

```text
[shipment-case-e2e] error: 平台链路未就绪
```

先执行：

```bash
./scripts/status-local.sh
```

再检查：

```text
runtime/logs/compose.log
runtime/logs/platform-bff.log
runtime/logs/link-booking-service.log
runtime/logs/load-planning-service.log
```

常见原因：

```text
8080 尚未启动完成
Python 没有注册到 Nacos
Nacos 心跳暂时未稳定
MySQL 未健康
端口被其他程序占用
```

### 16.2 Python Alembic 迁移失败

检查：

```text
runtime/logs/link-booking-service-alembic.log
runtime/logs/load-planning-service-alembic.log
```

如果 8200 是启动前就存在的外部进程，一键脚本不会擅自迁移它正在使用的数据库，而会执行
`alembic current --check-heads`。数据库不在当前 head 时，脚本会停止，避免在缺表状态下
继续运行。

### 16.3 V9 没有执行或菜单没出现

检查：

```text
runtime/logs/platform-bff.log
platform_bff_lab.flyway_schema_history
```

Flyway 在 Java BFF 启动时执行。如果 8080 一直是旧 Java 进程，新代码没有真正重启，就
不能假设 V9 已经运行。

可以先安全停止由本项目脚本管理的应用进程：

```bash
./scripts/stop-local.sh
```

再重新运行：

```bash
./scripts/run-local.sh core
```

MySQL 和 Nacos 会保留，不会被 `stop-local.sh` 删除。

### 16.4 绑定资源返回 400

当前 Java 平台语义中，待绑定资源不存在会返回 HTTP 400。Python 内部接口原始状态是
422，Java BFF 将其归一为平台输入错误。常见原因：

```text
装载任务编号不存在
LINK 申请编号不存在
编号拼写错误
请求连到了不是当前数据集的服务实例
```

不要为了绕过 400 而直接向绑定表插入数据。先到专业工作台确认资源真实存在。只有
Shipment Case 案件编号本身不存在时，平台才返回 404。

### 16.5 返回 409

可能原因：

```text
expectedRevision 已过期
同一资源已经绑定到其他案件
重复案件编号或命令语义冲突
同一个幂等 key 被用于不同 payload
```

409 是明确业务结果。先 GET 最新案件并检查事实，不要无条件循环重试。

### 16.6 返回 502 或 503

在当前 Java BFF 语义中，可以先这样理解：

```text
503：Nacos 中没有可用 Python 实例；连接失败；连接或读取超时；Python 明确返回 503
502：上游协议错误、JSON 转换失败、其他 HTTP 客户端异常或未知上游错误
```

Shipment Case 专用 Java 客户端默认连接超时 2 秒、读取超时 15 秒。超时只限制等待时间，
不代表 Java 会自动重试，也不代表已经实现熔断。写命令结果未知时，安全重试仍必须复用
原 `Idempotency-Key`。

继续结合 Java 和对应 Python 日志判断。E2E 故意不打印上游错误正文、SQL 或环境变量。

### 16.7 为什么脚本错误信息比较短

脚本不会输出：

```text
请求体全文
响应正文全文
数据库连接串
环境变量
Token 或 API Key
```

终端输出只用于定位失败步骤。更深的诊断应在本机受控日志中完成，不能为了方便排查而把
所有内部错误直接回显给调用方。

## 17. E2E 运行后会留下哪些本地数据

脚本没有自动清理步骤。

每次成功运行会保留：

```text

├── 1 条 load_planning_tasks
├── 1 条 cargo_items
├── 1 条 pallet_specs
```

```text
DEMO-SHIP-E2E-*
SHP-E2E-*
```

保留数据有两个好处：

```text
可以在 Vue 页面继续查看审计结果
可以在 MySQL 中学习主表、绑定表、事件表和命令台账的关系
```

代价是重复运行会积累更多合成记录。当前还没有实现测试数据自动归档或安全清理策略。
