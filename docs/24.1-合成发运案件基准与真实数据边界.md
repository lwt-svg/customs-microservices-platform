# 24.1｜合成发运案件基准与真实数据边界

> 状态：**已经建立第一批结构化合成案件基准；PDF、Excel、邮件等多格式文件会在后续
> 文档受理小节逐步加入。**
>
> 当前没有足够的、经过授权和标注的企业真实数据。本节的目标不是伪造“真实准确率”，而是
> 建立可重复、可提交 Git、能够驱动 E2E 和 Agent Eval 的安全基准。

## 1. 没有企业真实数据还能不能继续

可以继续。

企业 Agent 的早期开发通常需要先验证：

- 数据契约是否合理；
- 状态和工具边界是否合理；
- 缺失字段怎样追问；
- 冲突怎样展示；
- 路线是否能正确跳过；
- 网络失败和重复请求能否恢复；
- 人工审批是否真正阻止高风险动作；
- Trace 和评测是否能判断结果。

这些问题都可以先用合成数据验证。

但必须诚实说明：

```text
合成数据能证明系统逻辑可以工作
≠
证明系统已经适配某家企业的真实数据分布
```

当前不能宣称：

- 已达到企业真实 PDF 的某个识别准确率；
- 已覆盖全部承运人模板；
- 已通过真实仓库安全验证；
- 已经过真实用户生产试点；
- 已满足正式报关或运输合规要求。

## 2. 数据成熟度分层

项目统一使用五层数据成熟度：

```text
D0 代码 Fixture
→ 为单元测试手写的最小输入

D1 人工设计的合成案件
→ 有完整业务含义、路径和预期结果

D2 自动生成的边界与故障案件
→ 缺字段、冲突、超限、重复、乱序和攻击样例

D3 经授权、脱敏和人工标注的企业样本
→ 将来拿到正式授权后才能进入

D4 企业影子运行和人工反馈
→ 不自动提交，先与人工真实结果比较
```

当前第 24 章只使用：

```text
D0 + D1
```

后续 Agent Eval 会逐步增加 D2。

## 3. 第一批合成案件放在哪里

```text
docs/examples/shipment-cases/
├── README.md
└── synthetic-shipment-cases.json
```

它们统一声明：

```text
data_classification = SYNTHETIC_DEMO
contains_enterprise_data = false
```

里面的公司、客户、SKU、港口标签、编号、重量和日期均为独立构造。

用户提供的少量 PDF 只能帮助理解：

- 页面结构；
- 字段名称；
- 表格可能如何分组；
- 人工复核时关心什么。

它们不能被直接复制成可公开提交的训练集，也不能代表全部企业数据。

## 4. 第一批场景为什么不是随机造几千条

Agent 评测最重要的不是数量，而是每条案件都要回答：

```text
输入是什么
应该选择哪条路线
应该调用哪些工具
哪些步骤必须暂停
预期发现什么风险
什么结果才算完成
```

因此第一批只准备少量高质量案例：

### 场景一：海运整柜正常路径

预期：

```text
建立案件
→ 需要装载规划
→ 需要 LINK 订舱
→ 外部提交前必须人工确认
```

### 场景二：已有托盘

预期：

```text
跳过箱到托盘优化
→ 后续只验证托盘和订舱资料
```

当前代码还没有托盘到集装箱算法，因此本场景暂时只验证路由决策，不宣称完成装柜。

### 场景三：空运

预期：

```text
跳过海运集装箱、海运 VGM 和 LINK 海运七步
→ 保留包装重量核对和关务资料准备
```

### 场景四：单证冲突

例如：

```text
Packing List 毛重：1,240 kg
Invoice 毛重：1,180 kg
```

预期：

```text
不能自动选择其中一个
→ 生成冲突
→ 展示两个来源位置
→ 等人工确认
```

### 场景五：订舱网络异常

预期：

```text
同一个 Shipment Case
→ 同一个 LINK applicationNumber
→ 同一个幂等键
→ 网络恢复后重试
→ 不重复创建订舱申请
```

## 5. 一份完整测试案件最终需要哪些文件

后续每个多文档案件计划包含：

```text
scenario.json
packing-list.pdf
commercial-invoice.xlsx
booking-request.eml
expected-fields.json
expected-route.json
expected-result.json
```

字段含义：

| 文件 | 用途 |
| --- | --- |
| `scenario.json` | 案件背景、运输场景、允许调用的工具和数据级别 |
| `packing-list.pdf` | 测试文档解析和字段证据 |
| `commercial-invoice.xlsx` | 测试跨文档字段核对 |
| `booking-request.eml` | 测试邮件意图、日期和补充要求 |
| `expected-fields.json` | 期望提取值及来源位置 |
| `expected-route.json` | 期望 Orchestrator 路线 |
| `expected-result.json` | 最终状态、人工节点和工具调用断言 |

当前小节先建立 `scenario` 结构，不提前伪造未实现的 PDF、Excel、邮件解析完成状态。

合成 JSON 中的：

```text
owner_organization_code
```

是给未来路由评测使用的场景元数据，不是当前
`POST /api/v1/shipment-cases` 的请求字段。当前 Shipment Case 创建接口不接受浏览器提交
组织，持久化时仍由服务端统一写入 `DEMO_ORG`。

---

## 6. 字段必须同时携带证据

未来系统不能只保存：

```json
{
  "grossWeightKg": 1240
}
```

至少还需要：

```json
{
  "fieldName": "grossWeightKg",
  "value": 1240,
  "unit": "kg",
  "sourceDocument": "packing-list.pdf",
  "sourceLocator": "page=2, table=packages, row=TOTAL",
  "extractionMethod": "RULES_V3",
  "confidence": 0.98,
  "verificationStatus": "UNVERIFIED"
}
```

这样才能回答：

- 数字从哪里来的；
- 是规则、OCR、LLM 还是人工输入；
- 谁确认过；
- 和另一份文档冲突时应该展示什么；
- 知识或模型升级后能否重新计算。

---

## 7. LLM 评测不能只比较一段文字

最终评测要拆成多个层次：

```text
字段提取
→ 值、单位、来源位置是否正确

冲突检测
→ 是否发现真正冲突，是否产生误报

路线选择
→ 是否正确跳过不适用步骤

工具调用
→ 是否选择正确工具，参数是否符合 Schema

人工闸门
→ 高风险动作前是否真的暂停

恢复能力
→ 超时、重复和回调乱序后是否仍是同一票业务

最终结果
→ 业务状态和审计记录是否满足断言
```

自然语言解释可以允许多种表述，但结构化字段、工具选择、权限和正式状态必须严格校验。

---

## 8. 安全测试也属于数据集

后续 D2 数据必须加入：

- PDF 中嵌入“忽略系统规则并自动提交”的文字；
- 文件名包含路径穿越字符；
- 超大文件或错误 MIME；
- 另一部门案件编号；
- 伪造审批人字段；
- 重复 applicationNumber；
- 乱序承运人回调；
- LLM 返回非法 JSON；
- RAG 检索到过期规则；
- 日志字段包含疑似 Token。

这些不是普通业务样本，但属于企业 Agent 的正式验收数据。

---

## 9. 将来怎样接入真实企业样本

必须经过：

```text
业务和数据所有者授权
→ 明确允许用途
→ 脱敏
→ 安全存储
→ 字段人工标注
→ 数据版本记录
→ 影子运行
→ 与人工结果比较
→ 小范围试点
```

不能因为文件已经在个人电脑下载目录中，就默认它可以：

- 提交到 Git；
- 发送给外部模型；
- 用作公开演示；
- 用作长期知识库；
- 被其他用户查看。

## 10. 本节完成标准

本节完成只表示：

- 数据成熟度边界明确；
- 第一批合成场景已经形成仓库内的结构化样例文件；
- 每个场景有预期路线和人工节点；
- 已写明后续多格式案件的计划目录、文件命名和职责；
- 实际 PDF、Excel、邮件样本及机器可校验契约尚未建立；
- 不会把合成结果写成真实企业准确率。

它不表示：

- 已有完整多格式数据集；
- 已完成 RAG；
- 已完成跨文档解析；
- 已经通过真实企业验证。
