## 4. 为什么新增 `get_session_factory`

原有 CRUD 接口使用：

```python
async def get_session() -> AsyncIterator[AsyncSession]:
    async with SessionLocal() as session:
        yield session
```

这种依赖适合一次请求只使用一个数据库会话的场景：

```text
HTTP 请求
-> 查询或写入
-> 提交
-> 请求结束后关闭会话
```

Shipment Case 绑定 LINK 申请时多了一次远程 HTTP：

```text
检查案件和幂等
-> 调用 LINK 验证申请
-> 锁住案件并写绑定
```

如果一个请求从头到尾只拿着同一个隐式事务，远程 LINK 超时期间也会占着数据库事务。以后
并发量增加后，这会拖长锁等待和连接占用。

本节新增：

```python
def get_session_factory() -> async_sessionmaker[AsyncSession]:
    return SessionLocal
```

Service 可以按阶段创建会话：

```text
会话 A：短读取，随后关闭
-> 没有案件数据库事务时调用 LINK
-> 会话 B：短写入，提交后关闭
```

> 后续修订说明：24.3 收口时加入独立命令台账后，当前阶段 A 已演进为短锁行事务，并可能
> 在“资源已属于本案件”时登记成功 `NO_OP`。阶段 B 的核心边界没有改变：远程 LINK 等待
> 期间仍然没有案件事务，也不持有案件行锁。

### 4.1 为什么不能直接在 Service 中导入全局 `SessionLocal`

如果 Service 写死：

```python
from app.db.session import SessionLocal
```

测试覆盖 `get_session()` 也没有用。Shipment Case 会绕过内存 SQLite，尝试连接开发者本机
MySQL。

当前 API 通过 FastAPI 依赖注入会话工厂：

```text
get_session_factory
-> ShipmentCaseService
-> 每个事务阶段创建 AsyncSession
```

测试再覆盖同一个依赖：

```text
测试 session_factory
-> 内存 SQLite
-> 三阶段流程仍使用同一套测试数据库
```

这解释了 `tests/conftest.py` 为什么同时覆盖：

```text
get_session
get_session_factory
```

前者服务原有 API，后者服务 Shipment Case 的多阶段事务。

## 5. LINK 内部地址怎样配置

`app/core/config.py` 新增：

```python
link_booking_internal_base_url: str = "http://127.0.0.1:8000"
shipment_resource_verify_timeout_seconds: float = Field(
    default=3.0,
    gt=0,
    le=30,
)
```

对应环境变量：

```dotenv
LINK_BOOKING_INTERNAL_BASE_URL=http://127.0.0.1:8000
SHIPMENT_RESOURCE_VERIFY_TIMEOUT_SECONDS=3
```

本机一键启动时，LINK 仍在 8000 端口，所以旧 `.env.local` 不补这两项也能使用默认值。

部署方式变化时，只改地址：

```text
本机
http://127.0.0.1:8000

Docker Compose
http://link-booking-service:8000

Kubernetes
http://link-booking-service.<namespace>.svc.cluster.local:8000
```

当前实现只从配置读取 HTTP base URL，不使用 Nacos 发现 LINK。Docker Compose 和
Kubernetes 可以分别通过容器 DNS 和 Service DNS 解析配置中的主机名，但这些地址目前
只是目标部署示例，还没有在本节完成部署验收。

## 6. 为什么 Python 直接调用 LINK

平台正常入口仍然是：

```text
Vue
-> Java platform-bff
-> Python Agent Runtime
```

但 Agent Runtime 验证 LINK 申请时不会再绕回 Java：

```text
Agent Runtime
-> LINK Service
```

如果绕回 Java，调用链会变成：

```text
Java
-> Agent Runtime
-> Java
-> LINK
```

这种循环会增加超时传播和排错难度。Java BFF 当前负责浏览器统一入口、服务发现、DTO
转换和错误翻译；可信用户身份及其向 Python 的传递仍待后续安全章节实现。Python 内部
业务服务之间使用明确的内部接口。

## 8. 这一节为什么没有新建总 LangGraph

Shipment Case 当前先建立：

```text
案件事实
资源引用
状态机
revision
幂等命令
审计事件
```

这些都是总编排依赖的稳定基础。此时直接新建 Shipment Orchestrator，会让 Graph 节点依赖
尚未确定的案件 API、文档模型和工具合同。

第 23 章的装载 LangGraph 继续运行，不需要修改。后续总 Graph 会调用：

```text
Shipment Case 工具
装载工具
LINK 工具
文档与 RAG 工具
人工审批工具
```

业务事实仍写 MySQL，Graph checkpoint 只保存流程游标。两者不会合并成一张表。

## 10. 可以在哪里打断点

学习 FastAPI 依赖注入时，可在以下位置打断点：

```text
app/db/session.py
-> get_session_factory()

app/api/shipment_cases.py
-> get_shipment_resource_verifier()
-> get_shipment_case_service()
```

观察一次资源绑定请求时：

```text
同一个 session_factory
-> 创建本地资源验证会话
-> 创建案件阶段 A 会话
-> 关闭
-> 创建案件阶段 C 会话
```

按当前最终代码调试时，阶段 A 可能出现一次 `NO_OP` 写入。上面的记录保存了本节最初完成
会话工厂改造时的理解，24.3 再继续解释命令台账修订后的事务细节。

不要把“创建了多个 AsyncSession”理解为“启动了多个 Python 服务”。这些会话只是同一进程
中的短生命周期数据库工作单元。
