## 1. 这一小步接到了哪里

24.3 的浏览器外调用方式是：

```text
curl / Swagger
-> Python Agent Runtime
-> Shipment Case Service
-> MySQL
```

本节增加 Java BFF 后，调用链变为：

```text
调用方
-> Java ShipmentCaseController
-> Java ShipmentCaseService
-> DiscoveryClient 查询 Nacos
-> RestClient 调用 Python
-> Python ShipmentCase API
-> Python Service / Repository
-> MySQL
```

Java 对外暴露的平台路径：

```text
/api/v1/platform/shipment-cases
```

Python 继续使用自己的内部路径：

```text
/api/v1/shipment-cases
```

本节没有把 Python 业务逻辑改写成 Java。Java 只增加了一层稳定的平台入口。

## 2. 为什么浏览器不直接长期调用 Python

如果 Vue 分别记住每个 Python 服务的地址，它会逐渐承担这些工作：

```text
识别不同服务的主机和端口
适配 camelCase 与 snake_case
理解每个服务不同的错误正文
处理内部服务迁移
决定哪些内部字段可以暴露
```

这些事情放在 Java BFF 更合适。Vue 只调用平台 API，Java 再根据服务名找到 Python。

这一层的职责被刻意限制为：

```text
平台 HTTP 入口
请求基础校验
服务发现
DTO 转换
幂等请求头透传
错误状态翻译
```

Java 不负责：

```text
案件状态机
revision 递增
幂等记录查询
资源真实性验证
案件事件写入
Shipment Case 数据持久化
```

这些业务规则已经在 24.3 的 Python 领域服务中实现，不应在 Java 再维护一份。

## 3. Python 学习者怎样理解这一层 Java

可以先用熟悉的 Python 概念建立对应关系：

| Java 代码 | 接近的 Python 概念 | 本项目中的作用 |
| --- | --- | --- |
| `@RestController` | FastAPI `APIRouter` | 声明 HTTP 路由。 |
| Java `record` | Pydantic Model 或只承载数据的 dataclass | 定义请求、响应形状。 |
| Jakarta Validation | Pydantic 字段校验 | 在进入 Service 前检查基础格式。 |
| `ShipmentCaseService` | 应用服务或 HTTP 适配器 | 调用 Python 并转换结果。 |
| `DiscoveryClient` | 从服务注册中心查询实例 | 根据服务名找 Python 地址。 |
| `RestClient` | `httpx.Client` | 发出 HTTP 请求。 |
| `ResponseStatusException` | FastAPI `HTTPException` | 让 Spring 返回指定 HTTP 状态。 |

这只是帮助阅读的对应关系。Java Bean Validation、Jackson 和 Spring MVC 有自己的执行
时机，不能把它们当成 Pydantic 的完全等价实现。

## 6. Controller 做了什么

文件：

```text
platform-bff/src/main/java/com/customsaffairs/platform/shipmentcase/
ShipmentCaseController.java
```

创建接口的核心代码是：

```java
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public ApiResponse<ShipmentCaseResponse> createCase(
        @Valid @RequestBody CreateShipmentCaseRequest request,
        @RequestHeader("Idempotency-Key") String idempotencyKey) {
    return ApiResponse.success(
            shipmentCaseService.createCase(request, idempotencyKey));
}
```

可以按执行顺序阅读：

```text
Spring 根据 @PostMapping 匹配请求
-> Jackson 把 JSON 转成 CreateShipmentCaseRequest
-> @Valid 执行基础字段校验
-> Spring 读取 Idempotency-Key
-> Controller 调用 ShipmentCaseService
-> Controller 用 ApiResponse 包装成功结果
```

Controller 没有注入 Repository，也没有写 SQL。它的每个方法都很短，因为业务规则不属于
这一层。

### 6.1 `@Valid` 校验到什么程度

创建请求会检查：

```text
caseNumber 非空、最大 64 字符、字符格式合法
caseName 非空、最大 128 字符
transportScenario 非空且能转换成已知枚举
description 最长 2000 字符
```

资源绑定请求会检查：

```text
resourceType 非空
resourceNumber 非空、最大 64 字符、字符格式合法
expectedRevision 必须大于 0
```

状态变更请求会检查：

```text
targetStatus 非空
expectedRevision 必须大于 0
reason 非空、最长 2000 字符
```

这些是 HTTP 输入的基础形状校验。下面这些仍由 Python 判断：

```text
案件是否存在
资源是否真实存在
revision 是否仍然有效
案件能否进入目标状态
同一资源是否已经属于其他案件
```

Java 不复制这些规则，避免以后 Python 改了状态机而 Java 忘记同步。

## 7. Java `record` 为什么分成两组

Java 21 的 `record` 适合定义不可变的数据载体：

```java
public record CreateShipmentCaseRequest(
        String caseNumber,
        String caseName,
        ShipmentTransportScenario transportScenario,
        String description) {
}
```

它会生成构造方法、访问器、`equals()`、`hashCode()` 和 `toString()`。访问字段时写：

```java
request.caseNumber()
```

而不是传统 Java Bean 的：

```java
request.getCaseNumber()
```

Shipment Case BFF 使用两组 record，是为了隔离两个接口契约。

### 7.1 平台 record

这些类型放在独立文件中，并声明为 `public`：

```text
CreateShipmentCaseRequest
BindShipmentCaseResourceRequest
ChangeShipmentCaseStatusRequest
ShipmentCaseResponse
ShipmentCaseResourceBindingResponse
ShipmentCaseEventResponse
```

它们表示：

```text
Vue <-> Java BFF
```

字段使用平台前端习惯的 camelCase，例如：

```text
caseNumber
transportScenario
expectedRevision
resourceBindings
occurredAt
```

### 7.2 Remote record

`ShipmentCaseService.java` 内部还有私有 record：

```text
RemoteCreateCaseRequest
RemoteBindResourceRequest
RemoteChangeStatusRequest
RemoteShipmentCase
RemoteResourceBinding
RemoteCaseEvent
```

它们表示：

```text
Java BFF <-> Python Agent Runtime
```

这些类型被声明为 `private`，Controller 和其他 Java 模块无法依赖它们。以后 Python 契约
调整时，改动可以集中在 BFF 的远程适配边界。

## 8. camelCase 怎样转换成 snake_case

Vue 创建案件时发送：

```json
{
  "caseNumber": "SHP-DEMO-FCL-001",
  "caseName": "上海至洛杉矶演示发运",
  "transportScenario": "SEA_FCL",
  "description": "合成数据案件"
}
```

Java 平台请求 record 接住 camelCase，再转换成远程请求：

```java
private record RemoteCreateCaseRequest(
        @JsonProperty("case_number") String caseNumber,
        @JsonProperty("case_name") String caseName,
        @JsonProperty("transport_scenario")
        ShipmentTransportScenario transportScenario,
        String description) {
}
```

发给 Python 的 JSON 变为：

```json
{
  "case_number": "SHP-DEMO-FCL-001",
  "case_name": "上海至洛杉矶演示发运",
  "transport_scenario": "SEA_FCL",
  "description": "合成数据案件"
}
```

Python 响应也先进入 `RemoteShipmentCase`。`toPlatformResponse()` 再把它转成平台
`ShipmentCaseResponse`，Spring 最后向 Vue 输出 camelCase。

```text
Vue camelCase
-> 平台 request record
-> remote request record + @JsonProperty
-> Python snake_case

Python snake_case
-> remote response record + @JsonProperty
-> toPlatformResponse()
-> 平台 response record
-> Vue camelCase
```

这里没有启用一个覆盖整个项目的全局命名转换策略。转换被限制在 Remote record 中，因此
不会意外改变组织、用户、菜单等已有平台 API。

### 8.1 枚举为什么在 Java 也有一份

Java 定义了：

```text
ShipmentCaseStatus
ShipmentResourceType
ShipmentTransportScenario
```

Java 枚举用于：

```text
校验平台输入是否为已知值
把 Python 响应转换成明确类型
减少代码中的任意字符串
```

Java 没有复制案件状态转移表。`DRAFT` 能否进入 `ACTIVE`、`ACTIVE` 能否进入
`COMPLETED`，仍然只由 Python 状态机决定。

## 9. Service 怎样找到并调用 Python

文件：

```text
platform-bff/src/main/java/com/customsaffairs/platform/shipmentcase/
ShipmentCaseService.java
```

Service 保存的不是固定主机地址，而是服务名：

```java
private static final String SERVICE_ID = "load-planning-service";
```

构建 URL 时执行：

```java
ServiceInstance instance = discoveryClient
        .getInstances(SERVICE_ID)
        .stream()
        .findFirst()
        .orElseThrow(...);
```

然后以 Nacos 返回的 `instance.getUri()` 为基础，追加：

```text
api / v1 / shipment-cases
```

因此 Java 代码没有写死：

```text
http://127.0.0.1:8200
```

本机端口或以后容器内地址变化时，只要 Python 以同一个服务名正确注册，Java 仍可找到它。

当前实现使用发现结果中的第一个实例：

```text
findFirst()
```

这已经满足本地单实例学习环境，但还不是多实例负载均衡方案。不能仅凭这一段代码宣称已经
具备生产级流量分配和故障摘除。

### 9.1 `RestClient` 的调用

写请求集中经过 `post()`：

```java
RemoteShipmentCase response = restClient.post()
        .uri(uri)
        .header("Idempotency-Key", requiredKey)
        .body(body)
        .retrieve()
        .onStatus(HttpStatusCode::isError, this::handleRemoteError)
        .body(RemoteShipmentCase.class);
```

读取列表时，Java 还需要保留泛型信息：

```java
ParameterizedTypeReference<List<RemoteShipmentCase>>
```

如果只写 `List.class`，Jackson 只能得到普通 Map 列表，不能可靠地反序列化成
`RemoteShipmentCase`。

### 9.2 为什么连接超时和读取超时要分开

本节初版 BFF 先完成了服务发现、DTO 转换和错误翻译，当时复用了通用 `RestClient`，没有
Shipment Case 专用截止时间。收口审查发现跨服务调用可能无限等待后，才增加
`ShipmentCaseClientProperties` 和 `ShipmentCaseRestClientConfiguration`。这段记录保留了
真实修订顺序。

如果跨服务调用没有明确截止时间，Python 未启动、端口不可达或请求处理一直不返回时，Java
工作线程可能长时间占住。Shipment Case 因此使用一个专用 `RestClient`：

```text
连接超时 connect timeout：默认 2 秒
读取超时 read timeout：默认 15 秒
```

两者不是一回事：

```text
连接超时
-> Java 在规定时间内没有与 Python 建立连接

读取超时
-> TCP 连接已经建立，但一次阻塞读取在规定时间内没有拿到响应数据
```

本机可以用环境变量覆盖：

```bash
export SHIPMENT_CASE_CONNECT_TIMEOUT=3s
export SHIPMENT_CASE_READ_TIMEOUT=20s
```

配置位置：

```text
platform-bff/src/main/resources/application.yml
```

绑定后的 Java 配置名是：

```text
platform.shipment-case.client.connect-timeout
platform.shipment-case.client.read-timeout
```

Spring 支持 `500ms`、`2s`、`1m` 等 Duration 格式。值必须大于 0；本机默认值只是当前
学习环境的安全边界，生产值要根据接口耗时分布和 SLO 重新评估。

`SimpleClientHttpRequestFactory` 的 read timeout 是底层 socket 读取超时，不是覆盖服务发现、
排队、连接和全部响应读取的严格“总请求截止时间”。本节先解决无限等待风险；以后如果要
做端到端 deadline、重试预算和熔断，需要在运维与韧性章节单独设计。

超时不等于重试，也不等于熔断。本节没有在 Java 自动重放写请求，因为创建、绑定和状态
推进都是业务命令；是否重试必须继续服从 `Idempotency-Key` 语义。

### 9.3 为什么不能直接修改通用 Builder

配置类先执行：

```java
restClientBuilder.clone()
```

再为克隆后的 Builder 安装带超时的 `SimpleClientHttpRequestFactory`。最后生成的 Bean 名为：

```text
shipmentCaseRestClient
```

`ShipmentCaseService` 通过 `@Qualifier` 只注入这个客户端。这样本节新增的 2 秒 / 15 秒
不会悄悄作用到 LINK、装载规划等其他模块。测试还会保留一个原始请求工厂，确认创建
Shipment Case 客户端后，原 Builder 构建出的其他客户端没有被修改。

## 10. `Idempotency-Key` 为什么必须原样透传

三个 POST 都要求：

```http
Idempotency-Key: browser-create-001
```

这个值描述的是“一次写命令”，不是案件业务字段，所以它放在 HTTP header 中，不写进
JSON DTO。

Java BFF 的处理原则是：

```text
不重新生成
不添加前缀
不 trim
不写入 Java 数据库
原样转发给 Python
```

真正的幂等判断仍由 Python 执行：

```text
相同 key + 相同请求
-> 返回已有结果

相同 key + 不同请求
-> HTTP 409
```

假设 Python 已经成功写入，但响应在网络中丢失。Vue 用原 key 重试，Java 必须继续转发
同一个 key，Python 才能识别这不是第二条业务命令。

Java Controller 把请求头声明为必填。调用方漏传时，Spring 会在进入业务方法前返回
HTTP 400。

## 11. 错误为什么需要翻译

Python 的状态码和错误正文面向 Python 服务边界。Vue 需要一组稳定的平台语义，不应依赖
FastAPI、Pydantic 或数据库异常的内部文字。

`handleRemoteError()` 当前使用下表：

| Python 返回 | Java 平台返回 | 平台含义 |
| --- | --- | --- |
| 400 | 400 | 请求不符合 Python 接口要求。 |
| 422 | 400 | Pydantic 输入错误，以及当前 Python 的“待绑定资源不存在”。 |
| 404 | 404 | 发运案件不存在。 |
| 409 | 409 | revision 冲突、幂等冲突或状态不允许。 |
| 502 | 502 | Python 依赖返回了错误协议或响应。 |
| 503 | 503 | 案件依赖服务暂时不可用。 |
| 其他错误状态 | 502 | 平台无法把它解释成已知业务错误。 |

Java 自己还会产生这些错误：

| 场景 | Java 状态码 |
| --- | --- |
| Nacos 中没有 `load-planning-service` 实例 | 503 |
| 请求字段未通过 Jakarta Validation | 400 |
| 缺少 `Idempotency-Key` | 400 |
| Python 成功状态却没有响应体 | 502 |
| 已发现实例，但连接失败或连接/读取超时 | 503 |
| 已连接且收到响应，但 HTTP 客户端或 JSON 转换失败 | 502 |

`handleRemoteError()` 不读取 Python 的响应正文，也不会把正文拼进
`ResponseStatusException`。例如 Python 返回：

```json
{
  "detail": "PYTHON_SECRET_DATABASE_DETAIL"
}
```

Java 只根据状态码生成平台文案。自动测试确认平台异常原因不包含上面的内部文字。

这项保护的准确含义是：

```text
当前 BFF 不向调用方回显 Python 错误正文
```

它不等于系统已经完成日志脱敏、统一 Trace、告警或生产安全审计。

当前还要注意一个容易混淆的细节：资源验证器找不到装载任务或 LINK 申请时，Python API
会把领域错误转换成 HTTP 422；Java 再统一转换成平台 HTTP 400。因此当前真实链路中的
“待绑定资源不存在”落在 400，而不是 404。以后如果要把资源不存在单独稳定为 404，需要
同时修改 Python 异常映射、Java 测试和 Vue 提示，不能只改页面文字。

### 11.1 为什么先捕获并重新抛出 `ResponseStatusException`

Service 中的调用通常使用：

```java
} catch (ResponseStatusException exception) {
    throw exception;
} catch (ResourceAccessException exception) {
    throw dependencyUnavailable(operation, exception);
} catch (RestClientException exception) {
    throw badGateway(...);
}
```

第一段保留已经翻译好的 400、404、409、502、503。第二段把连接不可达和连接/读取超时
稳定为 503，并使用固定平台文案，不拼接底层异常消息。最后一段才把其他 HTTP 客户端故障
统一转成 502。这个顺序也避免把已知 409 再误包装为 502。

### 11.2 当前错误响应外壳的边界

成功响应使用：

```text
ApiResponse<T>
```

当前项目还没有为 Shipment Case 增加统一的全局失败响应包装。本节测试保证的是 HTTP
状态和安全的平台原因，不应写成“所有成功与失败都已经使用同一种 JSON 外壳”。

## 12. 为什么 Java 不建 Shipment Case 表

这不是漏写，而是数据所有权设计。

Python 已经拥有：

```text
shipment_cases
shipment_case_resource_bindings
shipment_case_events
shipment_case_commands
```

如果 Java 再建一套案件表，一次状态变更会变成：

```text
写 Python 数据库
-> 再写 Java 数据库
-> 处理其中一次成功、另一次失败
-> 判断两份 revision 谁才是真的
```

这样会引入双写一致性问题。当前设计只保留一个事实来源：

```text
Python Agent Runtime
-> 拥有案件状态、revision、资源绑定、事件和命令台账

Java platform-bff
-> 查询、转换并返回这些事实
```

Java 工程中已经存在 JPA 和 Flyway，因为平台自己的组织、用户、角色、权限、菜单仍由 Java
拥有。这不代表每个经由 BFF 暴露的业务对象都要落一份 Java 表。

## 13. actor 和组织字段的真实边界

平台创建请求：

```text
CreateShipmentCaseRequest
```

没有这些字段：

```text
actorSubject
actorDisplayName
actorSource
responsibleOrganizationCode
```

所以它们不会进入 `ShipmentCaseService`，也不会出现在 Java 发给 Python 的
`RemoteCreateCaseRequest` 中。

但是当前 Jackson 配置会忽略请求 JSON 中未知的字段。测试故意发送：

```json
{
  "actorSubject": "MUST_NOT_REACH_PYTHON",
  "responsibleOrganizationCode": "FORGED_ORG"
}
```

该请求并不会仅因为这两个多余字段而被 Java 拒绝。准确结论是：

```text
未知 actor / organization 字段不会被 Java DTO 接收，也不会转发给 Python
```

不能写成：

```text
Java 已严格拒绝伪造 actor / organization
```

系统当前也没有完成：

```text
真实登录
Spring Security Session
RBAC 接口拦截
可信当前用户
可信当前组织
可信 actor 透传
```

Python 响应中的 `DEMO_ORG` 和 `SYSTEM_DEMO` 仍是服务端演示占位值，不代表真实已认证
用户。后续做可信身份时，应由 Java 的服务端会话产生内部身份上下文，不能接受浏览器自己
声明 actor。

## 14. 通过 Java BFF 手工请求

先启动本地完整核心服务：

```bash
./scripts/run-local.sh core
```

Java BFF 默认地址：

```text

```

Python 的本机端口仍然是 8200，但本节手工验证应优先请求 8080，确认 BFF 路径确实工作。

### 14.1 创建案件

```bash
curl -X POST \
  http://127.0.0.1:8080/api/v1/platform/shipment-cases \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: bff-create-shp-demo-fcl-001' \
  -d '{
    "caseNumber": "SHP-DEMO-FCL-001",
    "caseName": "上海至洛杉矶演示发运",
    "transportScenario": "SEA_FCL",
    "description": "只包含合成数据"
  }'
```

观察：

```text
HTTP 状态为 201
响应外层有 code / message / data
data 字段使用 camelCase
```

### 14.2 查询列表

```bash
curl http://127.0.0.1:8080/api/v1/platform/shipment-cases
```

### 14.3 绑定装载任务

先查询详情，使用响应中的最新 `revision`：

```bash
curl -X POST \
  http://127.0.0.1:8080/api/v1/platform/shipment-cases/SHP-DEMO-FCL-001/resources \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: bff-bind-shp-demo-fcl-001-load' \
  -d '{
    "resourceType": "LOAD_PLANNING_TASK",
    "resourceNumber": "LP-DEMO-0001",
    "expectedRevision": 1
  }'
```

`LP-DEMO-0001` 必须已经存在。Java 不查装载数据库，Python 会完成资源验证。

### 14.4 推进案件状态

绑定成功后再次使用最新 revision：

```bash
curl -X POST \
  http://127.0.0.1:8080/api/v1/platform/shipment-cases/SHP-DEMO-FCL-001/status \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: bff-activate-shp-demo-fcl-001' \
  -d '{
    "targetStatus": "ACTIVE",
    "expectedRevision": 2,
    "reason": "资料核对完成，进入处理中"
  }'
```

如果页面或命令使用了旧 revision，平台会返回 HTTP 409。调用方应先重新查询详情，再基于新
revision 生成一条新的业务命令。
